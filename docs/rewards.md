# 问答积分兑换（第一版）

入口：`/rewards`。页面包含奖励目录、我的积分、我的兑换；已验证邮箱的审核员可进入“Manage rewards”维护目录并处理订单。延续现有 Workers + D1 部署，新增迁移 `0004_rewards.sql` 和 `0005_reward_revision.sql`。

## 积分规则

- 同一用户回答同一问题，只对首个仍可见的有效回答记 10 分。
- 每个来自其他已验证邮箱真实用户的有效赞记 2 分。
- 被另一位提问者当前采纳的回答记 20 分。
- 提问者和回答者均须为已验证邮箱的真实账号；演示讨论、自问自答、已删除或隐藏内容不产生兑换积分。
- 取消点赞、改变采纳或下架内容后，相应积分自动调整；恢复有效内容后重新计算。不会重复“领取”同一份积分。

可用积分为当前有效贡献积分，减去待履约和已履约订单的成本。取消或拒绝待履约订单，会释放积分和库存。已兑换后贡献被撤回，余额可能出现欠额；页面显示待补积分并停止新兑换，后续贡献可抵补。

这是当前贡献的积分明细，不是不可变的资金流水。贡献列表至多显示 100 条，日期为原回答日期；钱包总额覆盖全部符合条件的贡献。订单保存独立的价格、名称、类型及商品版本快照和状态事件。等级 XP 继续使用原有逻辑，不因兑换扣减。积分不能提现或转让。

## 目录与履约

初始目录包含 3 件明确标记的 Demo 奖励，仅用于展示，不可兑换。没有虚构可履约商品或合作商。实际供应安排确认后，由审核员创建真实目录条目，设置积分价格、总配额、供应方、兑换条件和是否展示。

库存计算为总配额减去待履约和已履约订单数。下架商品保留历史订单；修改目录不会改变已下单的价格、名称、类型或版本。管理员不能把总配额降至已占用量以下。Demo 标记不可通过编辑变为真实商品。

会员在确认弹窗确认商品、积分和领取条件，可附 500 字以内备注。首版由管理员按已验证的账号邮箱线下联系履约，不在网站收集收货地址或付款信息，也不自动发送履约邮件。管理员在订单中填写券码、领取说明、物流参考或拒绝原因，仅本人和审核员可见。

订单状态：

- `pending`：已预留积分和库存，可由本人取消。
- `fulfilled`：管理员确认已履约，终态，不自动退款。
- `cancelled`：本人取消待履约订单，释放占用，终态。
- `rejected`：管理员拒绝待履约订单，释放占用，终态。

管理员不能处理自己的订单。同一最终状态和相同备注的重试保持幂等；不同终态不能互相覆盖。每个状态只保留一次对应的审计事件。

## 一致性与权限

`POST /api/rewards` 使用现有同源、请求大小、会话和限流校验。实际兑换和后台操作还严格要求邮箱已验证、非 Demo，包含本地环境。积分计算不依赖客户端、旧的 `users.xp` 或 `xp_events`。

新兑换在一条数据库 INSERT 中同时检查用户资格、目录状态、商品版本、价格、剩余库存和积分余额；幂等键以用户为范围。商品在确认期间被编辑，旧确认会被拒绝，要求刷新。相同请求重试依据原订单快照返回，不会多扣积分；改变同一键的商品、价格、版本或备注会返回冲突。

`GET /api/rewards` 公开目录，登录后仅附自己的钱包和最近 50 条订单。`?view=admin` 只向有权限的审核员返回完整管理目录及最多 100 条订单（待履约优先）。用户不能查询其他人的积分、备注、邮箱或券码。测试数据不会形成可用积分或可登录的奖励账号。

## 验证

```bash
pnpm typecheck
pnpm test
pnpm build
pnpm test:preview
```

积分 API 测试只允许本地地址，创建并清理独立的测试账号、内容和奖励；不会向线上写测试兑换订单。覆盖资格与撤销、幂等、商品改价/改条件、同时抢库存、同时使用余额、订单快照、取消/拒绝退款、终态、欠额和越权访问。

共享本地 SQLite 的测试文件按顺序运行，文件内部保留并发兑换检查，避免外部测试夹具写入与 Worker 连接争用。线上预览仍关闭注册，真实会员登录、邮件验证和实际奖品履约需要在开放服务前联调。
